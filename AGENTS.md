# AI agent instructions for svht_denoise

## What belongs in this file

Two things only:

- **Gotchas** — behaviour that will bite someone who reads the code and reasonably concludes otherwise.
- **Dead ends** — approaches that look promising in theory and were measured or tried, and did not pay.

Nothing else. No task history, no changelog, no restating what the layout or the tool obviously does. Every line here is loaded into every future context window, so it has to earn its place. Delete entries that stop being true; the code and the README are the record of what exists.

## Gotchas

- **nifti_io.c/h are vendored from upstream and out of scope.** A widely used, robust library that is not ours to tidy. Do not audit it, refactor it, or report findings against it. The Makefile builds it with warnings off on purpose, so that a clean build means something for the code we do own.
- **Dependencies are zlib, libm and pthreads, with two exceptions that were argued rather than assumed: zlib-ng, bundled, and Accelerate, macOS-only.** The rule still decides how problems get solved -- it is why the phase rotation in `dn_phase.c` needs a k-space low-pass and uses a provably equivalent 7-tap convolution rather than linking an FFT. What the two exceptions have in common is that NEITHER is something a user installs or the project ships: zlib-ng is a drop-in for a dependency already on the list, pinned as a submodule and linked statically, measured at ~3x on the write path; Accelerate is a system framework present on every macOS the tool targets, resolved at load like libSystem, adding nothing to the executable, and worth -36% CPU at large volume counts. A general BLAS is still refused, and the distinction is exactly that: it would be a thing to find, install and version. "It is faster" was never the bar and still is not.
- **The zlib-ng build falls back silently, and that changes what you are measuring rather than whether it works.** TWO things reach it: a non-recursive clone, and a build path containing any character outside `A-Za-z0-9._/-` (zlib-ng's own build cannot handle those, and the Makefile tests an ALLOW-LIST, so this is not just whitespace — a non-ASCII home directory is enough). A `ZLIBNG=` value other than `0` or `1` does NOT reach it and never did: that is a hard `$(error)`, which is the point, since `ZLIBNG=auto` once selected the system zlib silently. The system zlib is ~3x slower at writing `.nii.gz` and otherwise identical, so a benchmark from one clone is not comparable to one from another. `make` prints which library went in, on every build including a no-op one — read that line before trusting a timing. Releases refuse the fallback outright and prove the static link by checking the finished binary does not name `libz`, because the submodule merely being present does not mean it was the thing linked.
- **Output is byte-identical across thread counts, and that is a promise.** No `-ffast-math`, no reassociation, no reductions in the worker pool.
- **`dn_write_f32`/`dn_write_u16` mutate the `dn_image` they are handed** — datatype, dims, scaling, filenames — and do not restore it. Safe to call in any order; not safe to read geometry back out afterwards.
- **`nifti_set_filenames()` rewrites `nim->nifti_type` from the names it just built.** All four outputs share one `nim`, so without care the first `.hdr`/`.img` output silently switches every LATER extensionless output from `.nii` to `.hdr`/`.img` — names the collision check never modelled, which is how an output came to land on an input at exit 0. `write_image` now restores `ref->nifti_type` before touching filenames, and `dn_image` keeps that copy precisely because `nim`'s own does not survive the first write. Never resolve an output name from `nim->nifti_type` after a write.
- **A NaN comparison is false, so `if (x > worst)` fails OPEN, not closed.** `dn_grid_offset_mm` returned a clean 0.0 mm — "same grid" — for a NaN affine, because no corner ever updated the running maximum. Any "fails closed on non-finite" claim has to be checked at the point where the value is *produced*, not only where it is tested; the `!(off <= tol)` gate downstream was correct and still never saw the NaN.
- **The grid (affine) check is on `-phase` only, deliberately.** `dn_grid_offset_mm` gates the phase image at 0.001 mm; `dn_mask_build` compares nx/ny/nz and the volume count, and no affine at all. A mask legitimately arrives from another pipeline with a rewritten header, and rejecting those would break working command lines for no gain — a wrong mask costs voxels, a wrong phase silently corrupts every value. There is a comment at the site saying so; do not "fix" the asymmetry.
- **`make` pastes a variable's VALUE into a recipe as literal shell source, so `$(VAR)` in a recipe is an injection site.** `make macos-notarize VERSION='x";touch /tmp/PWNED;"'` created the file. `package_macos.sh` does validate VERSION and it made no difference — the shell had already run the injected command before the script started. Every release variable is therefore `export`ed and written `$$VERSION`, never `$(VERSION)`: through the environment a value cannot become syntax. It matters because the documented flow is `make macos-release VERSION=<tag>`, on the machine holding the signing key.
- **A static library carries its own deployment target, and mismatching it is quiet.** An unpinned zlib-ng build stamps `minos 26.0` into every object; linking that into a release built `-mmacosx-version-min=11.0` emits a wall of "built for newer macOS version" warnings but produces an executable whose OWN `minos` still reads 11.0 — so `package_macos.sh`'s minos gate passes and the package ships. `package_macos.sh` exports `MACOSX_DEPLOYMENT_TARGET` into the sub-make precisely so the two cannot disagree, and `make clean` deletes `src/.zlibng` so a dev-configured library can never survive into a release.
- **`productbuild --synthesize` hardcodes `hostArchitectures="x86_64,arm64"` and never looks at the payload.** Synthesizing from an x86_64-only component emits the identical line, so an arm64-only package silently advertises itself as installable on Intel — where macOS Installer accepts it and every later invocation dies with "Bad CPU type in executable". Nothing about the payload corrects this; `package_macos.sh` rewrites the attribute for both the signed and adhoc paths and fails closed if the rewrite does not take. That attribute is the only thing that actually refuses the install: the README and the Read Me pane can only ask, and the Read Me is not attached to an adhoc package at all.
- **Phase units cannot be inferred for data that does not span a full turn, and trying is worse than asking.** A range of `[-0.5, 0.5]` is half a radian or one whole cycle, and the file does not say which. An attempt to resolve it from the value magnitudes shipped briefly and silently broke cycle-encoded phase: the tool no-opped, returned the magnitude and reported success. `-phaseunits` exists for this; leave the default inferring from the observed span, which is right for anything that covers a turn.
- **Wall clock drifts upward across a long sweep and CPU time does not, so judge a few-percent change on CPU.** Over three rounds of a six-binary sweep the same baseline binary measured 91.3, 94.7 then 95.0 s of wall clock while its CPU time moved by a fifth as much: the machine warms, and whichever candidate happens to run late looks worse. `scripts/bench.sh` therefore alternates candidates and reverses the order every other round, and takes a median rather than a minimum. Its load-average gate is a LAGGING indicator on top of that — a benchmark that has just finished leaves a 1-minute average above 7 on an otherwise idle machine, so consecutive legs have to wait for it to decay or the second is refused by its own gate. Read the refusal rather than raising `MAXLOAD`; the floor on a given machine can also be permanent (an animated wallpaper holds a whole core here, which is why the gate cannot sensibly be set below about 2). Plugging in makes it WORSE before it gets better, because macOS schedules `mediaanalysisd`, `spotlightknowledged` and friends the moment a machine is on mains and idle.
- **Battery power and Low Power Mode halve the clock, and inflate CPU time as well as wall, so no column gives it away.** The identical pair of binaries measured 95 s and 189 s of wall on mains and on battery. What survives untouched is the RATIO between two candidates — 1.681x against 1.675x on that same pair — because alternation makes the state common-mode. So an A/B conclusion taken in the wrong power state is still sound while every absolute number in it is out by two. `scripts/bench.sh` refuses outright rather than warning (`ALLOW_LOWPOWER=1` overrides), because nothing in a recorded timing says afterwards which state produced it.

- **`dn_hypot` is not "NaN in, NaN out", and the asymmetry is real.** `dn_hypot(NaN, 0.0)` returns 0.0 — a comparison against a NaN is false, so `hi` takes the other operand and the `hi == 0.0` early return fires — while `dn_hypot(0.0, NaN)` returns NaN. `(Inf, NaN)` and `(NaN, Inf)` both give NaN where hypot must give Inf. Only `dn_hypot(p, e[i])` with an exactly-zero `e[i]` could swallow anything, and it is left unguarded on purpose: a NaN test on that fast path is the one thing the function exists to avoid. Two audit agents disagreed about this and only compiling it settled it — do not take a claim about non-finite behaviour on reading.

- **Peak RSS carries the WHOLE raw input buffer for the entire run whenever the input is not float32, and that is the normal case.** Measured on 100x100x58 x 138 (a series no longer in this repo) uint16: 775 MiB, against 623 MiB for the identical run from a float32 copy of the same data. The difference is 152 MiB, which is exactly the size of the raw buffer -- and `dn_nii.c` does free it, correctly and early. The allocator keeps it: a freed block that large is retained, and reused only if the NEXT large request fits inside it. Reproduced standalone -- with a 152.7 MiB hole, a following request of 100 or 150 MiB grows RSS by nothing while 200 or 305 MiB grows it by the full amount. The denoised series is float32, so on any narrower input it cannot fit, and the hole is dead weight until exit. `free()`, `madvise(MADV_FREE)`, `MADV_FREE_REUSABLE` and `malloc_zone_pressure_relief` were each tried and none returns the pages; the only real fix is to stop holding the raw buffer whole, i.e. convert in slabs as it is read. Whether the hole is reused is NOT deterministic, which is the part that wastes time: five identical runs measured 775, 775, 629, 775, 776 MiB on a uint16 input and 623 every time on a float32 copy of it. So peak RSS on this tool is bimodal by roughly the raw-buffer size, and a build that appears to have "improved" memory has usually just landed on the other side of that coin -- Accelerate appeared to save 145 MiB for exactly this reason and saves none. Do not "explain" a peak-RSS figure without checking the input datatype first.

- **A macOS build and a non-macOS one are NOT bit-identical to each other, by design.** The macOS default reduces through Accelerate's blocked `dsytrd`; everywhere else uses the reduction in `dn_eig.c`. Different algorithm, ~3e-10 relative L2 apart, rank maps identical. The promise the project makes is byte-identity ACROSS THREAD COUNTS within one build, and that still holds on both. `make ACCELERATE=0` reproduces the portable path on a Mac when you need to compare like with like. The build prints which reduction went in, on every build including a no-op one, exactly as it does for zlib.
- **The Accelerate binding and the deployment target are tied together.** The new LAPACK interface resolves `dsytrd$NEWLAPACK`, which first exists in macOS 13.3; releases target 14.0, the oldest macOS still receiving Apple security patches as of August 2026. Built against anything older, the binary links, packages, passes the minos gate AND the framework check, then dies at launch with a missing symbol -- nothing in the artefact says so beforehand. Below 13.3 the legacy CLAPACK spelling is required in `dn_eig.c` instead, and it still works, at the cost of a deprecation warning.

- **`dn_pt_t` is `double` under Accelerate and `float` otherwise, so anything that SIZES the patch buffer must say `sizeof(dn_pt_t)`.** `worker_bytes` in `dn_run.c` said `sizeof(float)`, which under-prices every worker by n*m*4 and lets the 1 GiB scratch cap admit more of them than the budget allows. Caught by review, not by a test -- the cap only binds at volume counts nothing here exercises, so it fails silently and only on someone else's data. BLAS has no mixed-precision syrk, which is the whole reason the type varies; `dsyrk` accumulates in the precision you hand it.

- **`make -j` defeated the flag stamp, and that reopened the sanitizer gate this file claims to have closed.** GNU Make 3.81 is what `/usr/bin/make` is on macOS, and under `-j` it plans each object against the stamp's mtime as it stood BEFORE the stamp's own recipe rewrote it. Measured: `make -j8 && make -j8 ACCELERATE=0` never ran the link, so the binary still had Accelerate in it while the build printed "the built-in reduction"; and `make -j8 && make -j8 ubsan-test` reported 78 passed with the eigensolver and patch kernel carrying no instrumentation at all. Homebrew's make 4.4.1 and any serial build are unaffected, which is exactly why it survived so long. The fix is that stale objects are now deleted at PARSE time, before the graph is planned -- a missing object cannot be mis-dated, where no amount of dependency ordering can help. Do not turn that back into a rule.

- **The large-series comparison is a PIPELINE comparison, not a kernel one.** `benchmark-large/` is 140x140x92 x 297 volumes at 1.5 mm with magnitude AND phase, b up to 3010 -- deliberately low SNR, and the biggest thing here. The MPPCA* arm (`benchmark-large/mrtrix.py`: rotate complex to real, then `dwidenoise`) includes a single-threaded NumPy rotation, where svht_denoise does the rotation itself inside the same run. Read any ratio between the two arms with that in mind.
- **`benchmark-large/mrtrix.py` filters the low-pass ONE VOLUME AT A TIME, and must keep doing so.** numpy's FFT promotes to complex128; at 140x140x92x297 that intermediate is 8 GiB with several live at once, which does not fit. The filter is independent per (slice, volume), so streaming is the same arithmetic -- verified byte-identical against the previous whole-array version, all three outputs. It takes MAG PHASE OUTDIR; only the 1.5 mm series has a phase image, so only that one goes through it.
- **`-degibbs` deliberately does NOT use Accelerate, and vDSP cannot rescue it.** `vDSP_DFT_zop_CreateSetupD` accepts only lengths `f*2^n` with `f` in {1,3,5,15}; measured, it refuses 100, 54 and 36 (`benchmark/`) and 140, 92 and 297 (`benchmark-large/`) -- every in-plane and volume count either dataset has -- while accepting 96, 120, 128 and 160. So `dg_fft.c` carries its own mixed-radix transform, and `dg.c` calls no BLAS. This is the one kernel here where reaching for Accelerate is WRONG; the rest of the tool still uses it for the eigensolver. Do not "add vDSP" without checking the length contract first -- the probe is four lines.

- **Timing `-degibbs` against `mrdegibbs` on `.nii.gz` measures zlib, not the kernel, and it has already REVERSED an answer once.** Our binary links zlib-ng and `mrdegibbs` links the system zlib, ~3x apart on the deflate; on the large series' 2 GB write that is most of a minute. Demonstrated on a since-replaced kernel, 140x140x92 x 297: writing `.nii.gz` it looked **1.26x faster on wall**, writing `.nii` it was **9% SLOWER on both wall and CPU**. The compressed gap also masquerades as better thread scaling -- it read as 9.7x parallel efficiency against 7.3x, where with I/O removed the two arms were identical at 12.7x and 12.6x. The numbers belong to a dead kernel; the trap does not. Always compare this kernel with uncompressed output. The same confound is why the MPPCA\* entry above insists it is a pipeline comparison.
- **The 7/8 path clamps its OUTPUT, that is reference behaviour, and deleting it is an 80x regression.** `plane_run_7_8` truncates negatives where the conventional path and 6/8 do not, which reads exactly like an unexamined magnitude assumption -- two independent audit agents called it a defect and one "proved" it harmless by checking that the undershoot without it is the same size as the other modes'. That is the wrong question. The right one is what the reference does: on the 7/8 phantom, **clamped and unclamped outputs differ by relative L2 1.3e-4, while the clamped output agrees with the reference to 1.6e-6**. So the reference clamps too, and removing it moves us ~80x further from the thing we validated against. Do NOT extend it to the other two paths either: `mrdegibbs` emits negatives (measured min -25.228 on the 7/8 phantom at full k-space), so clamping there would cost the byte-identity that is the whole verification story for the Kellner transcription.
- **`dn_degibbs` truncates negative INPUT, and that is a different decision from the one above.** The method assumes magnitude data, so the input is made to satisfy it rather than the assumption being left implicit; truncating rather than folding to `+|v|` is deliberate, since rectifying would turn zero-mean noise into a Rician-like floor and hand the TV window spurious steps. It is a NO-OP on magnitude input, which is exactly why it costs no `mrdegibbs` parity -- only a caller that fed signed data sees a change. It does mean `-phase` plus `-degibbs y` gives up the signed output the README otherwise promises; `-real` is unaffected. Clamping the input does NOT make the output non-negative, and conflating the two is the easy mistake: undershoot is created during the transform, so the conventional path still emits negatives (124 on the repo's signed fixture) after the input has been clamped. `make test` pins the input clamp by byte-identity against a pre-clamped fixture, and pins both halves of that distinction. One consequence is worth stating because it is not obvious: **`mrdegibbs` parity has a precondition, and our own output violates it.** feed a degibbs output back in and its negatives are truncated, where `mrdegibbs` would keep them. So the stage is NOT idempotent and is not a faithful `mrdegibbs` stand-in for anything already degibbsed or already signed. Nothing is wrong with the parity measurement -- it is taken on magnitude input, which is the only thing `mrdegibbs` is run on -- but do not extend the claim to a chained run.
- **`dn_testgen`'s fixtures are 9x9x3, and an ODD y dimension means 6/8 cannot run on any of them.** `mag-even` (9x10x3) is the only fixture 6/8 runs on at all -- `mag-shorty` (9x6x3) is even too, but its interleave is 3 and falls under `DG_MIN_DIM`; without it the entire 6/8 success path -- half-length axis, strided sub-image -- is executed by nothing, and a `-pF 0.875` test asserting only an exit code would pass against an identity transform. Both PF factors pin an RMS for that reason. Adding a factor means asking first which fixture shape it can even run on.
- **`-mask` is refused with `-degibbs y`, and re-zeroing is NOT the fix.** A masked run leaves hard zeros outside the mask, and a hard zero edge is exactly the discontinuity the Kellner method rings on. Measured on the repo's own fixtures before it was refused: **647 of 648 out-of-mask voxels came back non-zero, peaking at 255.6 against a data range of ~1000**, breaking the "outside the mask reads as zero" promise every other output keeps. Re-zeroing afterwards would restore that promise and hide the real damage, which is the ringing thrown INWARDS off the mask boundary into voxels that are inside it. `-degibbs o` refuses `-mask` too, for the different reason that it does no denoising at all.
- **A `make <FLAG>=<value> test` LEAVES THE BINARY IN THAT CONFIGURATION, and the next benchmark then measures it.** Caught in the act: after a verification sweep ran `make ACCELERATE=0 test`, `src/svht_denoise` stayed the portable build, and because `make clean` had also removed `src/.zlibng` it relinked the SYSTEM zlib -- the two slowest configurations at once, ~36% more CPU in the eigensolver and ~3x on the `.nii.gz` write. A long benchmark was well under way before anyone noticed the CPU time looked wrong. Nothing about the binary announces this: `otool -L` and `src/.build_flags` both tell you, and `make` prints the configuration on every build INCLUDING a no-op one, which is why that line exists. Read it, or run a bare `make`, immediately before timing anything.
- **`-degibbs` output is byte-identical between `ACCELERATE=1` and `ACCELERATE=0`, and that is worth preserving.** It is the only kernel here that can claim it -- the denoiser cannot, because `dsytrd`/`dsyrk` make the two builds differ by ~3e-10. Anything that puts a platform-specific path back into `dg.c` costs that property, so weigh it against the property and not only against the clock.
- **A VOLUME-TRUNCATED copy of the large series is the degibbs iteration fixture, and it is a faithful proxy rather than merely a small one.** 24 volumes, uncompressed. Degibbs works per 2D plane, so cutting volumes cuts the plane COUNT and leaves the n = 140 transform under test untouched -- verified on the kernel of the day, where the fixture's ratio to `mrdegibbs` tracked the full 297-volume series' to within 2%. It is an order of magnitude quicker (seconds, not a minute) and its peak RSS is a few hundred MiB rather than 4 GiB, which matters because a benchmark that fills memory disturbs the next one. Make one with `FSLOUTPUTTYPE=NIFTI fslroi benchmark-large/svht_denoise/denoised.nii.gz <out> 0 24`. TIMING ONLY: that series is denoised output and is signed (1,033,112 negatives in the first 24 volumes, min -7784.4), so the input clamp puts an `mrdegibbs` comparison on it outside the parity precondition above. Absolute figures are deliberately omitted here -- they were measured on a kernel since replaced, and README carries the current ones.
- **Writing multi-GB outputs wakes `mdwrite`, which then holds a whole core and refuses your next benchmark.** Spotlight indexes every `.nii` a benchmark writes; it was measured at 99.5% of a core with nothing else running, and it is why `bench.sh`'s load gate kept refusing after a large sweep. It is self-inflicted and it does pass -- wait for it rather than raising `MAXLOAD`, and gate on `mdwrite`/`mds_stores` CPU as well as on load average, since the load figure alone recovers first.

- **An audit agent copying the working tree filled the disk to 100%, and 102 MB of untracked user data vanished in the same window.** Cause never established; the data was not in the Trash and not anywhere on disk afterwards. Whatever the mechanism, the lesson is cheap: audit agents get READ-ONLY instructions AND no reason to `cp -a` the repo, because untracked datasets sit inside it and a full filesystem is a hostile place for whatever runs next. Scope their scratch work to files they create.

## Dead ends

- **Use `make ubsan-test` / `asan-test` / `tsan-test`, never `make ubsan && make test`.** The two-command form rebuilds uninstrumented under the second command's default `OPT` and reports green having exercised nothing — verified by injecting signed overflow, which the one-invocation target caught and the two-command sequence passed clean. Worse, it did not reproduce reliably, so a spot check can miss it. All three run clean on Xcode 26.6 / clang 21. `dg_fft.h` documents its scratch as `maxradix` elements and `dg.c` allocates `nmax`, which is larger; an out-of-tree harness sized it at EXACTLY `maxradix` to prove the contract, so do not narrow that field away without replacing the check. (Sanitizers were broken machine-wide until Xcode 26.4 — Apple bug 171762808, unrelated to this project; the global notes carry the detail.)
- **Never pass `CFLAGS=` on the command line to a sanitizer target.** `CFLAGS = $(OPT) $(WARN)` and those targets set `OPT` in a sub-make, so a command-line `CFLAGS=` wins and the instrumentation vanishes from every object built from `$(CFLAGS)`. Today that does not reach the tests, but by luck rather than design: `NIFTI_CFLAGS` reads `$(OPT)` directly, so `nifti_io.o` alone stays instrumented and the link dies on undefined sanitizer symbols (measured, clang 21). Tidy `NIFTI_CFLAGS` to use `$(CFLAGS)` "for consistency" and the target goes back to building clean, running green, and having checked nothing. Environment `CFLAGS` is already defended against (plain `=`, not `?=`); the command line is not.
- **This project threads with pthreads, never OpenMP** — no `#pragma omp` anywhere; `otool -L` shows libSystem and Accelerate (plus libz on a `ZLIBNG=0` build, and nothing else on an `ACCELERATE=0` one). That is not the same as single-threaded: the `dn_run.c` worker pool is where the README's speedups come from. Worth stating because the usual Apple-Silicon sanitizer advice is about libomp and does not apply.
- **Threading the phase rotation.** The rotation is serial and costs ~370 ms of a ~2.1 s run on 104x104x72 x 21 (a series no longer in this repo) — about 18% of wall clock, though only ~2.7% of CPU time, which is why a single-sample wall-clock measurement badly misjudges it. Roughly half is the phase read and the min/max scan; the threadable per-volume compute is ~160 ms, so threading recovers under 8% of wall clock at the cost of new pthread machinery. Judged not worth it, and re-measured rather than assumed after the Gram blocking landed. Note the SHARE has risen from the 10% recorded earlier without the rotation getting slower: the denominator shrank, first when zlib-ng cut the deflate, then again with the blocking. The trade still holds because this dataset is 21 volumes and takes the full solver, where the blocking is worth ~9% rather than the ~38% it is worth at 138 volumes; a phase run at large N is where this entry would flip.
- **`security find-generic-password` cannot see notarization credentials, so do not gate on it.** `notarytool store-credentials` writes to the data-protection keychain; `security` queries only the legacy file-based one, so that lookup fails for *every* profile including working ones. There is no offline query for that keychain. `make check-notary-profile` asks `notarytool history` instead: one network round trip, which notarizing needs anyway, and strictly stronger — it proves the credentials AUTHENTICATE rather than that an item exists.
- **Returning the eigenvectors as ROWS instead of columns.** `dn_eig_vectors` builds its vectors contiguously, transposes them into columns, and its one caller then walks each column back at stride n -- 1104 bytes per element over a 152 kB array, twice per retained component. Deleting the transpose and making both projection passes sequential looks like free speed and a smaller function; measured over 7 alternating rounds on 100x100x58 x 138 (a series no longer in this repo) it is **0.4% slower on CPU and 1.1% on wall**. The strided read costs nothing because the retained rank is a median of 5, so only ~5 columns are ever touched and a constant stride is exactly what the prefetcher handles; the transpose it removes is the same 5 columns. Worse, the rewrite moved the output by 1.2e-11 relative L2 for reasons that survived a real hunt -- not the projection (both dot reductions compile to scalar ordered adds), not the fallback (never taken on that series), not thread non-determinism, not FMA contraction -- so it also spent exactness it had no way to justify.
- **Hand-writing a blocked (compact-WY) Householder reduction.** Answered by measurement rather than estimate, and then shipped the other way: Accelerate's blocked `dsytrd`/`dormtr` is worth **-14.4% wall and -16.2% CPU** on 100x100x58 x 138 (a series no longer in this repo) (58.6 -> 50.2 s, 741 -> 621 s), rel L2 3e-10 with the rank map identical; `cblas_dsyrk` for the Gram is worth a further **-23.0% wall and -24.7% CPU** (to 39.5 s / 474 s), for **-32.7% / -36.0%** together. Blocking the reduction DOES pay -- and 16% is what a mature, hardware-tuned implementation gets, so a hand-written one would land under it for far more risk, in the numerically subtlest code here. It is now the macOS default (`ACCELERATE=0` opts out, and is what other platforms build); the built-in reduction stays because it is the only one everywhere else. Note the apparent 145 MiB memory saving in that build is NOT Accelerate's doing; see the RSS gotcha above. `pt` being double does cost real memory, but tens of MiB, not hundreds.
- **A runtime block width in the Gram kernel.** `nb = min(4, n - j)` in place of `DN_GRAM_BLOCK`, so the scalar tail disappears, measures 1.3-3.6% SLOWER — the tail is written out precisely to keep the width a compile-time constant. A `static inline` helper taking `nb`, called with a literal 4 and then a literal 1, does measure bit-identical and marginally faster in isolation and would delete ~15 lines, but only in a microbenchmark of the loop; it leans on the inliner constant-propagating the width. If you take it, prove byte-identity against a preserved binary on both fixtures and the large series, then `scripts/bench.sh` it on the real workload — this session's whole record is of loop microbenchmarks and sample profiles pointing the wrong way.
- **LAPACK for the SMALL-n paths: `dsyevd` for the full solver, `dsterf` for the values-only tridiagonal.** Both measured, both rejected, and together they bound where Accelerate is worth reaching for. `dsyevd` replacing `tred2` + `tql2` on the n < DN_SPLIT_MIN path is **39% slower on wall and 46% on CPU** (1.32 -> 1.83 s, 14.63 -> 21.43 s over seven alternating rounds on 100x100x54 x 36 (`benchmark/`)); divide-and-conquer's setup and its 2n^2 workspace are not amortised at n = 36, where the hand-written specialisation is. `dsterf` for `tql2(NULL, ...)` on the split path is a wash at -0.3%, so that solver is already within ~1.5% of LAPACK's own. The pattern is consistent: Accelerate wins big where the work is O(n^3) on a large n and can reach AMX -- the Gram (11x in isolation, -24% of the run) and the reduction (-16%) -- and loses on anything small or already specialised. Do not reach for a library on the strength of the first two results without measuring.

- **Expressing the degibbs transform as a MATRIX MULTIPLY through `cblas_zgemm`, to reach AMX where an FFT cannot.** Built, shipped, tuned, then deleted. Precomputed DFT matrices with the 41 subvoxel ramps folded in, so a whole plane's shifts were one multiply on the AMX units -- it achieved **865 GFLOPS against `mrdegibbs`'s 35**, i.e. ~25x the throughput, and STILL LOST, because a direct DFT asks for **28x the flops** of an FFT. Measured, CPU: ahead by 22% at n = 104, behind by **49%** at n = 140, crossing over near n = 115, and in-plane matrices only grow. Replacing it with `dg_fft.c` also returned 206 MiB at n = 140 and removed ~150 lines, a per-worker scratch budget with its own tuning constant, and the platform divergence. The general lesson is the one the LAPACK entry reaches independently: **AMX pays for O(n^3) work you cannot avoid, never for O(n^3) work you chose.**
- **A Bluestein transform for degibbs, over vDSP's power-of-two FFT.** The obvious answer to "vDSP cannot do length 140", and measured before writing it: a length-140 Bluestein through a 512-point `vDSP_DFT_ExecuteD`, INCLUDING the pack and unpack that our interleaved `double _Complex` layout forces, costs **1.51 us** -- competitive, so it was never rejected on arithmetic. It is moot: adapting Eigen's kissfft gave a NATIVE mixed-radix transform for any length, and padding 140 up to 512 is ~14x the butterflies of transforming 140 directly. Only revisit if a length ever needs a radix `dg_fft.c` handles badly, and note its generic butterfly is O(p^2) for a large prime factor.
- **Trusting a single-threaded microbenchmark of the degibbs kernel -- twice, in one session.** Blocking the (now deleted) `zgemm` to take a whole plane at once measured **2.0x** isolated and **6%** on the real threaded workload: the loop modelled one worker reusing a shared matrix, where 14 workers already share it and instead contend over the grown output block. Separately, a probe of the portable matmul predicted a cache fix that measured bit-identical and within noise, because clang had already done it. Both cost a wrong prediction said out loud before the workload corrected it. Measure this kernel on a volume-truncated copy of the large series, never on a loop.

- **Writing the degibbs input truncation as `if (x < 0.0f) x = 0.0f;`.** The obvious spelling, and it does NOT vectorise: turning a conditional store into an unconditional one would invent a write C11 forbids, so clang emits a scalar compare-and-branch per element. `fmaxf(x, 0.0f)` measures **71.2 ms -> 34.3 ms on 2.14 GB**, which is within 1% of a loop that only reads and writes -- i.e. the memory-bandwidth wall, so hand-written NEON and alignment hints measured identically and buy nothing. `fmaxf` also maps NaN and -Inf to 0, which is wanted, and leaves +Inf alone. Do not "simplify" it back.
- **Replacing `conv_x`'s interior/edge split with one wrapped loop.** Measured 4.1x slower in that function (21 ms -> 86 ms) for 12 fewer lines, output byte-identical. The split stays.
- **Testing the rotation by cross-checking phase encodings against each other.** It looks like a strong test and is nearly worthless on its own: every encoding runs the same arithmetic, so a changed binomial tap moves both sides equally and cancels. Mutation testing confirmed it — altering a kernel coefficient broke no test. `make test` therefore also pins two recorded RMS values, which is the only thing there that would notice.
