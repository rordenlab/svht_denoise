# AI agent instructions for svht_denoise

## What belongs in this file

Two things only:

- **Gotchas** — behaviour that will bite someone who reads the code and reasonably concludes otherwise.
- **Dead ends** — approaches that look promising in theory and were measured or tried, and did not pay.

Nothing else. No task history, no changelog, no restating what the layout or the tool obviously does. Every line here is loaded into every future context window, so it has to earn its place. Delete entries that stop being true; the code and the README are the record of what exists.

## Gotchas

- **nifti_io.c/h are vendored from upstream and out of scope.** A widely used, robust library that is not ours to tidy. Do not audit it, refactor it, or report findings against it. The Makefile builds it with warnings off on purpose, so that a clean build means something for the code we do own.
- **Dependencies are zlib, libm and pthreads, with two exceptions that were argued rather than assumed: zlib-ng, bundled, and Accelerate, macOS-only.** The rule still decides how problems get solved -- it is why the phase rotation in `dn_phase.c` needs a k-space low-pass and uses a provably equivalent 7-tap convolution rather than linking an FFT. What the two exceptions have in common is that NEITHER is something a user installs or the project ships: zlib-ng is a drop-in for a dependency already on the list, pinned as a submodule and linked statically, measured at ~3x on the write path; Accelerate is a system framework present on every macOS the tool targets, resolved at load like libSystem, adding nothing to the executable, and worth -36% CPU at large volume counts. A general BLAS is still refused, and the distinction is exactly that: it would be a thing to find, install and version. "It is faster" was never the bar and still is not.
- **The zlib-ng build falls back silently, and that changes what you are measuring rather than whether it works.** TWO things reach it: a non-recursive clone, and a build path containing any character outside `A-Za-z0-9._/-` (zlib-ng's own build cannot handle those, and the Makefile tests an ALLOW-LIST, so this is not just whitespace — a non-ASCII home directory is enough). A `ZLIBNG=` value other than `0` or `1` does NOT reach it and never did: that is a hard `$(error)`, which is the point, since `ZLIBNG=auto` once selected the system zlib silently. The system zlib is ~3x slower at writing `.nii.gz` and otherwise identical, so a benchmark from one clone is not comparable to one from another. `make` prints which library went in, on every build including a no-op one — read that line before trusting a timing. Releases refuse the fallback outright and prove the static link by checking the finished binary does not name `libz`, because the submodule merely being present does not mean it was the thing linked.
- **Output is byte-identical across thread counts, and that is a promise.** No `-ffast-math`, no reassociation, no reductions in the worker pool.
- **`dn_write_f32`/`dn_write_u16` mutate the `dn_image` they are handed** — datatype, dims, scaling, filenames — and do not restore it. Safe to call in any order; not safe to read geometry back out afterwards.
- **`nifti_set_filenames()` rewrites `nim->nifti_type` from the names it just built.** All four outputs share one `nim`, so without care the first `.hdr`/`.img` output silently switches every LATER extensionless output from `.nii` to `.hdr`/`.img` — names the collision check never modelled, which is how an output came to land on an input at exit 0. `write_image` now restores `ref->nifti_type` before touching filenames, and `dn_image` keeps that copy precisely because `nim`'s own does not survive the first write. Never resolve an output name from `nim->nifti_type` after a write.
- **A NaN comparison is false, so `if (x > worst)` fails OPEN, not closed.** `dn_grid_offset_mm` returned a clean 0.0 mm — "same grid" — for a NaN affine, because no corner ever updated the running maximum. Any "fails closed on non-finite" claim has to be checked at the point where the value is *produced*, not only where it is tested; the `!(off <= tol)` gate downstream was correct and still never saw the NaN.
- **The grid (affine) check is on `-phase` only, deliberately.** `dn_grid_offset_mm` gates the phase image at 0.001 mm; `dn_mask_build` compares nx/ny/nz and the volume count, and no affine at all. A mask legitimately arrives from another pipeline with a rewritten header, and rejecting those would break working command lines for no gain — a wrong mask costs voxels, a wrong phase silently corrupts every value. There is a comment at the site saying so; do not "fix" the asymmetry.
- **`make` pastes a variable's VALUE into a recipe as literal shell source, so `$(VAR)` in a recipe is an injection site.** `make macos-notarize VERSION='x";touch /tmp/PWNED;"'` created the file. `package_macos.sh` does validate VERSION and it made no difference — the shell had already run the injected command before the script started. Every release variable is therefore `export`ed and written `$$VERSION`, never `$(VERSION)`: through the environment a value cannot become syntax. It matters because the documented flow is `make macos-release VERSION=<tag>`, on the machine holding the signing key.
- **A static library carries its own deployment target, and mismatching it is quiet.** An unpinned zlib-ng build stamps `minos 26.0` into every object; linking that into a release built `-mmacosx-version-min=11.0` emits a wall of "built for newer macOS version" warnings but produces an executable whose OWN `minos` still reads 11.0 — so `package_macos.sh`'s minos gate passes and the package ships. The Makefile inherits `MACOSX_DEPLOYMENT_TARGET` from the environment for the zlib-ng build precisely so the two cannot disagree, and `make clean` deletes `src/.zlibng` so a dev-configured library can never survive into a release.
- **`productbuild --synthesize` hardcodes `hostArchitectures="x86_64,arm64"` and never looks at the payload.** Synthesizing from an x86_64-only component emits the identical line, so an arm64-only package silently advertises itself as installable on Intel — where macOS Installer accepts it and every later invocation dies with "Bad CPU type in executable". Nothing about the payload corrects this; `package_macos.sh` rewrites the attribute for both the signed and adhoc paths and fails closed if the rewrite does not take. That attribute is the only thing that actually refuses the install: the README and the Read Me pane can only ask, and the Read Me is not attached to an adhoc package at all.
- **Phase units cannot be inferred for data that does not span a full turn, and trying is worse than asking.** A range of `[-0.5, 0.5]` is half a radian or one whole cycle, and the file does not say which. An attempt to resolve it from the value magnitudes shipped briefly and silently broke cycle-encoded phase: the tool no-opped, returned the magnitude and reported success. `-phaseunits` exists for this; leave the default inferring from the observed span, which is right for anything that covers a turn.
- **Wall clock drifts upward across a long sweep and CPU time does not, so judge a few-percent change on CPU.** Over three rounds of a six-binary sweep the same baseline binary measured 91.3, 94.7 then 95.0 s of wall clock while its CPU time moved by a fifth as much: the machine warms, and whichever candidate happens to run late looks worse. `scripts/bench.sh` therefore alternates candidates and reverses the order every other round, and takes a median rather than a minimum. Its load-average gate is a LAGGING indicator on top of that — a benchmark that has just finished leaves a 1-minute average above 7 on an otherwise idle machine, so consecutive legs have to wait for it to decay or the second is refused by its own gate. Read the refusal rather than raising `MAXLOAD`; the floor on a given machine can also be permanent (an animated wallpaper holds a whole core here, which is why the gate cannot sensibly be set below about 2). Plugging in makes it WORSE before it gets better, because macOS schedules `mediaanalysisd`, `spotlightknowledged` and friends the moment a machine is on mains and idle.
- **Battery power and Low Power Mode halve the clock, and inflate CPU time as well as wall, so no column gives it away.** The identical pair of binaries measured 95 s and 189 s of wall on mains and on battery. What survives untouched is the RATIO between two candidates — 1.681x against 1.675x on that same pair — because alternation makes the state common-mode. So an A/B conclusion taken in the wrong power state is still sound while every absolute number in it is out by two. `scripts/bench.sh` refuses outright rather than warning (`ALLOW_LOWPOWER=1` overrides), because nothing in a recorded timing says afterwards which state produced it.

- **`dn_hypot` is not "NaN in, NaN out", and the asymmetry is real.** `dn_hypot(NaN, 0.0)` returns 0.0 — a comparison against a NaN is false, so `hi` takes the other operand and the `hi == 0.0` early return fires — while `dn_hypot(0.0, NaN)` returns NaN. `(Inf, NaN)` and `(NaN, Inf)` both give NaN where hypot must give Inf. Only `dn_hypot(p, e[i])` with an exactly-zero `e[i]` could swallow anything, and it is left unguarded on purpose: a NaN test on that fast path is the one thing the function exists to avoid. Two audit agents disagreed about this and only compiling it settled it — do not take a claim about non-finite behaviour on reading.

- **Peak RSS carries the WHOLE raw input buffer for the entire run whenever the input is not float32, and that is the normal case.** Measured on 100x100x58x138 uint16: 775 MiB, against 623 MiB for the identical run from a float32 copy of the same data. The difference is 152 MiB, which is exactly the size of the raw buffer -- and `dn_nii.c` does free it, correctly and early. The allocator keeps it: a freed block that large is retained, and reused only if the NEXT large request fits inside it. Reproduced standalone -- with a 152.7 MiB hole, a following request of 100 or 150 MiB grows RSS by nothing while 200 or 305 MiB grows it by the full amount. The denoised series is float32, so on any narrower input it cannot fit, and the hole is dead weight until exit. `free()`, `madvise(MADV_FREE)`, `MADV_FREE_REUSABLE` and `malloc_zone_pressure_relief` were each tried and none returns the pages; the only real fix is to stop holding the raw buffer whole, i.e. convert in slabs as it is read. Whether the hole is reused is NOT deterministic, which is the part that wastes time: five identical runs measured 775, 775, 629, 775, 776 MiB on a uint16 input and 623 every time on a float32 copy of it. So peak RSS on this tool is bimodal by roughly the raw-buffer size, and a build that appears to have "improved" memory has usually just landed on the other side of that coin -- Accelerate appeared to save 145 MiB for exactly this reason and saves none. Do not "explain" a peak-RSS figure without checking the input datatype first.

- **A macOS build and a non-macOS one are NOT bit-identical to each other, by design.** The macOS default reduces through Accelerate's blocked `dsytrd`; everywhere else uses the reduction in `dn_eig.c`. Different algorithm, ~3e-10 relative L2 apart, rank maps identical. The promise the project makes is byte-identity ACROSS THREAD COUNTS within one build, and that still holds on both. `make ACCELERATE=0` reproduces the portable path on a Mac when you need to compare like with like. The build prints which reduction went in, on every build including a no-op one, exactly as it does for zlib.
- **The Accelerate binding and the deployment target are tied together.** The new LAPACK interface resolves `dsytrd$NEWLAPACK`, which first exists in macOS 13.3; releases target 14.0, the oldest macOS still receiving Apple security patches as of August 2026. Built against anything older, the binary links, packages, passes the minos gate AND the framework check, then dies at launch with a missing symbol -- nothing in the artefact says so beforehand. Below 13.3 the legacy CLAPACK spelling is required in `dn_eig.c` instead, and it still works, at the cost of a deprecation warning.

- **`dn_pt_t` is `double` under Accelerate and `float` otherwise, so anything that SIZES the patch buffer must say `sizeof(dn_pt_t)`.** `worker_bytes` in `dn_run.c` said `sizeof(float)`, which under-prices every worker by n*m*4 and lets the 1 GiB scratch cap admit more of them than the budget allows. Caught by review, not by a test -- the cap only binds at volume counts nothing here exercises, so it fails silently and only on someone else's data. BLAS has no mixed-precision syrk, which is the whole reason the type varies; `dsyrk` accumulates in the precision you hand it.

- **`make -j` defeated the flag stamp, and that reopened the sanitizer gate this file claims to have closed.** GNU Make 3.81 is what `/usr/bin/make` is on macOS, and under `-j` it plans each object against the stamp's mtime as it stood BEFORE the stamp's own recipe rewrote it. Measured: `make -j8 && make -j8 ACCELERATE=0` never ran the link, so the binary still had Accelerate in it while the build printed "the built-in reduction"; and `make -j8 && make -j8 ubsan-test` reported 78 passed with the eigensolver and patch kernel carrying no instrumentation at all. Homebrew's make 4.4.1 and any serial build are unaffected, which is exactly why it survived so long. The fix is that stale objects are now deleted at PARSE time, before the graph is planned -- a missing object cannot be mis-dated, where no amount of dependency ordering can help. Do not turn that back into a rule.

## Dead ends

- **Use `make ubsan-test` / `asan-test` / `tsan-test`, never `make ubsan && make test`.** The two-command form rebuilds uninstrumented under the second command's default `OPT` and reports green having exercised nothing — verified by injecting signed overflow, which the one-invocation target caught and the two-command sequence passed clean. Worse, it did not reproduce reliably, so a spot check can miss it. All three run clean on Xcode 26.6 / clang 21. (Sanitizers were broken machine-wide until Xcode 26.4 — Apple bug 171762808, unrelated to this project; the global notes carry the detail.)
- **Never pass `CFLAGS=` on the command line to a sanitizer target.** `CFLAGS = $(OPT) $(WARN)` and those targets set `OPT` in a sub-make, so a command-line `CFLAGS=` wins and the instrumentation vanishes from every object built from `$(CFLAGS)`. Today that does not reach the tests, but by luck rather than design: `NIFTI_CFLAGS` reads `$(OPT)` directly, so `nifti_io.o` alone stays instrumented and the link dies on undefined sanitizer symbols (measured, clang 21). Tidy `NIFTI_CFLAGS` to use `$(CFLAGS)` "for consistency" and the target goes back to building clean, running green, and having checked nothing. Environment `CFLAGS` is already defended against (plain `=`, not `?=`); the command line is not.
- **This project threads with pthreads, never OpenMP** — no `#pragma omp` anywhere, `otool -L` shows only libSystem (plus libz on a `ZLIBNG=0` build). That is not the same as single-threaded: the `dn_run.c` worker pool is where the README's speedups come from. Worth stating because the usual Apple-Silicon sanitizer advice is about libomp and does not apply.
- **Threading the phase rotation.** The rotation is serial and costs ~370 ms of a ~2.1 s run on 104x104x72x21 — about 18% of wall clock, though only ~2.7% of CPU time, which is why a single-sample wall-clock measurement badly misjudges it. Roughly half is the phase read and the min/max scan; the threadable per-volume compute is ~160 ms, so threading recovers under 8% of wall clock at the cost of new pthread machinery. Judged not worth it, and re-measured rather than assumed after the Gram blocking landed. Note the SHARE has risen from the 10% recorded earlier without the rotation getting slower: the denominator shrank, first when zlib-ng cut the deflate, then again with the blocking. The trade still holds because this dataset is 21 volumes and takes the full solver, where the blocking is worth ~9% rather than the ~38% it is worth at 138 volumes; a phase run at large N is where this entry would flip.
- **`security find-generic-password` cannot see notarization credentials, so do not gate on it.** `notarytool store-credentials` writes to the data-protection keychain; `security` queries only the legacy file-based one, so that lookup fails for *every* profile including working ones. There is no offline query for that keychain. `make check-notary-profile` asks `notarytool history` instead: one network round trip, which notarizing needs anyway, and strictly stronger — it proves the credentials AUTHENTICATE rather than that an item exists.
- **Returning the eigenvectors as ROWS instead of columns.** `dn_eig_vectors` builds its vectors contiguously, transposes them into columns, and its one caller then walks each column back at stride n -- 1104 bytes per element over a 152 kB array, twice per retained component. Deleting the transpose and making both projection passes sequential looks like free speed and a smaller function; measured over 7 alternating rounds on 100x100x58x138 it is **0.4% slower on CPU and 1.1% on wall**. The strided read costs nothing because the retained rank is a median of 5, so only ~5 columns are ever touched and a constant stride is exactly what the prefetcher handles; the transpose it removes is the same 5 columns. Worse, the rewrite moved the output by 1.2e-11 relative L2 for reasons that survived a real hunt -- not the projection (both dot reductions compile to scalar ordered adds), not the fallback (never taken on that series), not thread non-determinism, not FMA contraction -- so it also spent exactness it had no way to justify.
- **Hand-writing a blocked (compact-WY) Householder reduction.** Answered by measurement rather than estimate, and then shipped the other way: Accelerate's blocked `dsytrd`/`dormtr` is worth **-14.4% wall and -16.2% CPU** on 100x100x58x138 (58.6 -> 50.2 s, 741 -> 621 s), rel L2 3e-10 with the rank map identical; `cblas_dsyrk` for the Gram is worth a further **-23.0% wall and -24.7% CPU** (to 39.5 s / 474 s), for **-32.7% / -36.0%** together. Blocking the reduction DOES pay -- and 16% is what a mature, hardware-tuned implementation gets, so a hand-written one would land under it for far more risk, in the numerically subtlest code here. It is now the macOS default (`ACCELERATE=0` opts out, and is what other platforms build); the built-in reduction stays because it is the only one everywhere else. Note the apparent 145 MiB memory saving in that build is NOT Accelerate's doing; see the RSS gotcha above. `pt` being double does cost real memory, but tens of MiB, not hundreds.
- **Linking a general BLAS as a dependency.** Still declined -- see the dependency rule; Accelerate is admitted because it is a system framework, not because it is fast.
- **A runtime block width in the Gram kernel.** `nb = min(4, n - j)` in place of the literal, so the scalar tail disappears, measures 1.3-3.6% SLOWER — the tail is written out precisely to keep the width a compile-time constant. A `static inline` helper taking `nb`, called with a literal 4 and then a literal 1, does measure bit-identical and marginally faster in isolation and would delete ~15 lines, but only in a microbenchmark of the loop; it leans on the inliner constant-propagating the width. If you take it, prove byte-identity against a preserved binary on both fixtures and the large series, then `scripts/bench.sh` it on the real workload — this session's whole record is of loop microbenchmarks and sample profiles pointing the wrong way.
- **Replacing `conv_x`'s interior/edge split with one wrapped loop.** Measured 4.1x slower in that function (21 ms -> 86 ms) for 12 fewer lines, output byte-identical. The split stays.
- **Testing the rotation by cross-checking phase encodings against each other.** It looks like a strong test and is nearly worthless on its own: every encoding runs the same arithmetic, so a changed binomial tap moves both sides equally and cancels. Mutation testing confirmed it — altering a kernel coefficient broke no test. `make test` therefore also pins two recorded RMS values, which is the only thing there that would notice.
